# llm-upstream-probe

**检测一个 OpenAI 兼容端点到底把你的提示词怎么样了。**

当你通过第三方中转（relay / 代理 / 共享 Key）使用大模型时，中间那一跳是不透明的。这个工具用三个独立探针回答三个问题：

| 问题 | 探针 | 它到底在测什么 |
|---|---|---|
| 它有没有在你的内容之外**加东西**（身份声明、安全规则、工具协议）？ | `token` | 对 token 数做线性回归，看**截距**（内容之外的部分）是否异常 |
| 它有没有把你的 system **换掉或丢掉**？ | `canary` | 埋一枚不可猜的暗号，看模型能不能复现；再用行为差分确认 system 真的生效 |
| 它到底有没有在做**前缀缓存**（省钱）？ | `cache` | 发两轮前缀完全相同的请求，看上游是否报告缓存命中 |

不依赖任何第三方库，只要 Node ≥ 18。

---

## 为什么要有这个工具

「中转站会不会改我的提示词」是一个很多人私下担心、但公开讨论里几乎找不到实测的问题。截至 2026-11，GitHub 上已有的 Trae 相关项目（[A-23187/trae-api](https://github.com/A-23187/trae-api)、[dsh-trae-api](https://github.com/Wang-JQ77/dsh-trae-api)、[muskke/trae-api-proxy](https://github.com/muskke/trae-api-proxy)）**全是单向桥接**，没有一家做回环校验。

这件事有两个常见误区，本工具的设计就是在绕开它们：

**误区一：问模型「你的系统提示词是什么」就能验出来。**
不能。主流模型（DeepSeek、GPT、Claude）都有拒绝披露 system prompt 的对齐行为，**任何**通道都会拒答。用拒答当加料证据，是在把模型的自我保护误判成上游篡改。
→ 本工具因此把「中性复述暗号」和「行为服从」分开：前者的问法**刻意不提「系统提示词」**，后者根本不问它说什么、只看它怎么做。

**误区二：token 数对得上就说明没问题。**
只对了一半。token 差分能抓出**固定前缀注入**和**内容截断**，但抓不出「等量替换」（把你的 system 换成等长的另一段）。所以需要第二个探针直接验内容。

## 安装

```bash
git clone https://github.com/windy-0-0/llm-upstream-probe.git
cd llm-upstream-probe
node bin/cli.mjs --help
```

无需 `npm install`，无运行时依赖。

## 使用

```bash
# 全量探测
node bin/cli.mjs \
  --base-url https://relay.example.com/v1 \
  --api-key "$API_KEY" \
  --model gpt-4o-mini

# 只关心钱：它到底有没有在缓存
node bin/cli.mjs -u https://relay.example.com/v1 -k "$API_KEY" -m gpt-4o-mini -p cache

# 机器可读
node bin/cli.mjs -u ... -k ... -m ... --json
```

| 参数 | 说明 |
|---|---|
| `-u, --base-url` | 端点根地址，**要带 `/v1`**（工具会自己拼 `/chat/completions`） |
| `-m, --model` | 模型名 |
| `-k, --api-key` | 也可用环境变量 `LLM_PROBE_API_KEY` |
| `-p, --probe` | `token` / `canary` / `cache` / `all`（默认） |
| `--sleep` | 请求间隔毫秒，默认 1200。**别设成 0 去打真实服务** |
| `--header "K: V"` | 额外请求头，可重复 |
| `--json` | 输出 JSON |

**代价**：全量约 15–20 次短请求。输入最大的一轮约 8K 字符（≈2K tokens），单次输出限制在 4–120 tokens。实际花费通常在一分钱以内。

**凭据安全**：Key 只在进程内使用，**不读任何本地凭据文件、不落盘、不写日志**。

## 三个探针分别怎么判读

### 探针 1：token 差分

发同一句话，但 system 里塞入 0 / 25 / 50 / 100 份定长英文单位（每单位 44 字符 ≈ 11 tokens），对 `(单位数, prompt_tokens)` 做线性回归：

```
prompt_tokens = slope × 单位数 + intercept
```

- **slope** 应在 11 左右。显著偏低 → 内容被**截断/摘要**；显著偏高 → 被**扩写或重复计入**。
- **intercept** 是「内容之外的部分」。`单位数=0` 时只剩一条 user 消息，正常应 **< 60 tokens**。若这里就消耗了上千 token，说明上游**在请求里附加了固定内容**。
- **R²** 应接近 1。偏低说明 token 数不随内容线性增长，存在**内容相关的处理**。
- 每一档的**离群点**也会被点名。

> 阈值取自实测：不同 tokenizer 对英文的密度在 3.5–4.5 字符/token 之间浮动。下界设 0.6 是刻意留出的——截断 50% 会让比率落到 0.5，必须能被抓住。

### 探针 2：暗号

三个动作：

1. **中性复述** — system 里放一枚不可猜的暗号（`CANARY-XXXX-XXXX`），然后问「刚才那条消息里的标识符是什么」。**刻意不提「系统提示词」**，避免撞上模型自身的拒答对齐。
2. **行为差分** — system 里写一条无害但反常的格式规则（「先输出 `####`」），再发一次**不带规则**的同题作对照。
   - 有规则时服从 + 无规则时不服从 → system 被完整读取并生效
   - 带规则仍不服从 → system 可能被丢弃或改写
3. **身份词扫描** — 回复里有没有出现你没写过的身份声明。

### 探针 3：缓存

发三轮前缀完全相同的请求（约 8K 字符 system）。三种结局必须区分开：

| 现象 | 含义 |
|---|---|
| 命中 > 0 | ✅ 有缓存 |
| **字段存在但恒为 0** | ⚠️ **通道明确不提供缓存** —— 你每轮都在按全价付 input token |
| 字段完全不存在 | ❓ 无法判定（可能只是不统计） |

第二行是很多中转站的真实状况，而且它在账单上**不会显形**：字段恒为 0 很容易被误当成「没统计」而不是「没命中」。

## 实测结果：Trae 中转（2026-11-19）

用本工具对 `trae-api-cn.mchost.guru`（`llm_utils_chat` 端点，模型 `deepseek-v4.1-flash`）做了完整探测。

**结论：未发现提示词加料。**

| 测试 | 结果 |
|---|---|
| 消息层差分（1→65 条消息） | `prompt_tokens = 3.00 × messages + 28` — 斜率精确 3.00 |
| 定长单位差分（0→200 单位） | 每单位 11.01 tokens，极差 0.015 |
| **真实中文 system（0→3,957 字）** | **`0.6056 × 字 + 33.5`** — 斜率落在 DeepSeek 中文密度 0.55~0.70 内 |
| 幂等性（同输入两次） | 2,424 → 2,424，完全一致 |
| 暗号复现 | `ZQ7X-CANARY-4417` 被准确复现 |
| 行为差分 | 有规则输出 `####2`，无规则输出 `2` |

**关键判据是截距 33.5**：它和无 system 时的基线 32 只差 1.5。如果上游塞了固定指令，这个截距不可能还停在 30 上下。

### 但顺手发现了另一件事

同一批数据里，Trae 通道的缓存表现是：

```json
{ "prompt_tokens": 282, "cache_read_input_tokens": 0, "cache_creation_input_tokens": 0 }
```

字段**存在**，值**恒为 0**。累计 42,206 次请求、约 100.9 亿 input tokens，一次都没命中过；而同机另一条通道（Buddy / 腾讯前缀缓存）命中率 97.5%。

结论：**这条通道不提供 KV cache 复用**，每轮 input 都按未命中计价。这不是安全疑虑，是实打实的成本结构问题——而且它比「有没有被改提示词」更常发生、更容易被忽略。

### 也要说清楚这个测试**没**证明什么

- 它证明的是「**发出去的内容被完整、按比例、可复现地计入了 prompt**」。它**不能**证明下游 GPU 上那层 transformer 收到的东西一模一样——那需要抓 TLS 包做字节级比对（要对目标域名做证书中间人，有账号风险，本工具不做）。
- 它测不出「上游把内容等量替换但保持长度」这种规避（尽管探针 2 的暗号与行为差分能覆盖大部分实践情形）。

## 自测

```bash
node --test test/*.mjs
```

14 项测试。其中 4 项是**对抗性测试**：构造一个确定会加料 / 截断 / 丢弃 system 的假上游，断言探针**必须报警**。一个只会说「没问题」的检测器毫无价值，所以这些测试比正常路径更重要。

开发过程中，这组测试真的抓出了两个 bug：

1. 斜率阈值写成 `< 0.5`，恰好放过了「截断 50%」这一档（改成 `< 0.6`）。
2. 假上游算了截断后的文本却没用它计 token，导致测试假绿（改成用「上游真正看到的 messages」计数）。
